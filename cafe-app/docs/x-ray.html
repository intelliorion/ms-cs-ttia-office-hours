Creators' Café · the operator app · architecture

An X-ray of the Café app

One local app on one laptop, the IDE's AI behind a connector, three layers of understanding over the ideas, and three stages that use them. Every claim here is drawn from the code as it stands; the paths are real so each one can be checked.

0 · The story in one minute

What this is, and why it is built this way

Ideas arrive at the Café as emails, spreadsheets and PDFs, and once they are in, nobody can answer the questions that matter: who else is doing this, what does it depend on, and what breaks if a system or a tool changes. The answer is one local app that runs on the operator's own laptop, uses the AI the operator already has in their IDE, and keeps everything as files in one folder. Over the ideas it builds three layers of understanding. The property graph holds the facts as stated on the forms. The knowledge graph gives every thing one name, derives the links nobody typed, and says where each link came from. Deep read embeds what people actually wrote, so the app can quote it. Three stages, the decision, the design series and the roadshow, read those layers and write back to the record, and the AI never changes anything without a click. When the Café outgrows one laptop, the AI connector points at a Firm AI Gateway and the file writers point at Postgres or Snowflake, and everything in between stays as it is.

1 · The X-ray

Everything runs on the operator's laptop, in one process, from one folder

There is no server, no database and no service: one Node process, one workspace folder, and the AI that is already on the machine.

What it is

The app is a single Node process started with npm run cafe start. It listens on 127.0.0.1 only, so nothing on the network can reach it. The same process serves the built user interface from web/, answers the JSON routes the interface calls, rebuilds the graph, runs Deep read's index, spawns the AI, and runs the three stages. The same TypeScript tree also builds the command-line tool, which imports a submission export, checks the ontology and writes the JSON-LD export without starting the server.

Why it is built this way

One operator runs the Café. The constraint was never scale; it was that nothing may be installed on a server and nothing may leave the machine. So the whole state is one folder the operator can zip, copy or delete, and the AI is whichever assistant is already approved for their IDE. A change to the ontology in src/graph/ontology.ts is seen by the server, the interface, the CLI and the tests at once, because they are the same code. There is no second runtime, no migration, and no deployment step beyond npm install.

How it works, in steps

  1. The operator starts the app. It creates the workspace folders that are missing, loads rules/, and serves the interface on port 4100.
  2. The browser asks for the state. The server reads every idea folder, rebuilds the graph in memory, and returns stars, links and charts as JSON. The interface draws them as a star field.
  3. Anything the operator does that needs the AI, such as "suggest a decision", becomes one task. The connector codes the names, spawns the AI with the prompt on standard input, checks the reply against a schema, decodes the names, and shows a card.
  4. A click on the card writes the result into the idea folder. Writing a file touches Deep read's upkeep, which re-reads only the passages that changed, and the next graph read includes the new fact.

What changes when it scales

Only the two dashed boxes. The connector would gain a provider file for a Firm AI Gateway, and the four file writers would sit behind a store adapter for Postgres or Snowflake. The browser, the routes, the graph build, the inference rules and the stages would not change. Section 9 walks through both paths.

3 · How the AI is connected

The AI reads a coded prompt and returns a checked structure; the operator clicks

The AI never sees a name, never touches a file, and never changes the graph by itself: it answers a question in JSON, and Do it is a human click.

What it is

The app does not have an AI of its own. It uses the assistant the operator already has for their IDE, in the order Claude Code, then the GitHub Copilot CLI, then a VS Code helper, and uses the first one that is present on the machine. The operator can pin one of them, or "No AI", in rules/settings.yaml. A fourth provider, the fake, is put first only when the environment says CAFE_AI_FAKE=1; the tests and the guided tour run on it, so a whole round can be exercised without a model.

Why it is built this way

Three reasons. The assistant is already approved, so no new AI service needs approval. The prompt and the reply stay on the machine, so no data leaves. And every call is bounded: a child process in an empty temporary folder, the environment stripped of every CAFE_* variable, every built-in tool disabled, no MCP servers, no saved session, one turn, a hard timeout and a cap on the reply. The AI can read the prompt and nothing else. The VS Code helper is the one provider that is not a child process: it is an HTTP call to a helper on the local machine, found through a port and token in the operator's home folder, with the same cap on the reply.

How a call works, in steps

  1. A task is chosen. There are about fifteen named tasks in src/ai/tasks.ts: extract, review-suggest, feature-list, tool-pick, design-step, design-diagram, design-plan, design-kit, roadshow-prep, roadshow-deck, data-understand, data-step, understand, agent, look and ping. Each one has a prompt builder, a JSON schema and a timeout.
  2. The names are coded. Every star the text names is replaced by a code, longest name first, whole words only: a person becomes [P1], a team [T1], an idea [I1], a system [S1]. The AI is given the legend for everything except people, who are listed by type alone. A conversation keeps its codes, so [P1] in the first message is still [P1] in the tenth.
  3. The provider runs. The prompt goes on standard input, never on the command line. For a picture, Claude Code is allowed a single Read on a single file in an otherwise empty folder, and nothing else.
  4. The reply is checked. The first balanced JSON object in the text is parsed and validated against the task's schema by a small local validator: type, required keys, no extra keys, enumerations, lengths, item counts. A reply that fails is sent back once, headed by what was wrong, if at least fifteen seconds of the task's time remain. Nothing from the refused reply is used.
  5. The names are put back and the result is shown as a card, or fills a form. It is written into the record only when the operator clicks Do it, or saves the form.

What changes when it scales

A provider is one file that implements the Provider interface in src/ai/connector.ts: an id and label, available(), and complete(prompt, { timeoutMs }), with an optional look() for pictures. A Firm AI Gateway provider is that file plus an HTTPS call with the firm's token, built the way the VS Code helper already is. The coding of names, the schema check, the retry and the cards stay exactly as they are, because they sit on either side of the provider and never inside it.

4 · Where the data lives

Everything is a file in one folder, and every fact says which line put it there

Delete the data folder and the app rebuilds it from the imports and the operator's own log; there is nothing a database would have to protect that a file does not already hold.

What it is

The workspace has two halves. rules/ is the operator's configuration: settings, the stage definitions, and the three knowledge-graph files, entities.yaml, inference.yaml and ontology.yaml. data/ is everything the Café made or was given, and it is safe to delete in whole or in part, even while the app runs.

Under data/ideas/ there is one folder per idea, named by its Café id and a slug. The record itself is idea.yaml. Beside it sit the emails as they came in, a history.log of every action, and, as the idea moves on, approach.md and design.yaml from the design series, plan.md and a kit/ folder, a roadshow/ folder with the deck, and csic-handoff.md when it is routed to CSIC. Under data/graph/ the AI's reading is ai-links.jsonl, one link per line with its source, confidence, status and the idea it was read for, and the operator's changes are operator.jsonl, one dated edit per line: link, unlink, rename, merge, add, remove or alias, each with an id and a status that an undo flips rather than deletes. Deep read's index is three files under data/memory/. Exports go to data/exports/.

Why it is built this way

Two properties follow from files, and they are the two properties a database would have to keep. The first is that data/ can be rebuilt: the graph is never read from disk but recomputed from the idea folders, the AI links and the operator log on every read, and the index is rebuilt from the idea folders by a Run. The second is provenance: every link in the graph carries a source such as form:CAFE-2026-006:Submitter Name, ai:claude:challenge, operator or rule:needs+uses_data, so the answer to "why does the app believe that" is a line in a file the operator can open.

How a write works, in steps

  1. The writers are few and named: src/ideas/store.ts writes idea.yaml; src/graph/store.ts rewrites ai-links.jsonl; src/graph/operator.ts rewrites operator.jsonl; src/memory/index.ts writes the index, its state and the label vectors.
  2. Each one reads the whole file and writes it back through an atomic write, so a file is never torn, even if the process dies halfway.
  3. Every write into an idea folder goes through the workspace files layer, which names the idea and the kind of write on a touch bus. Deep read's upkeep listens there; so does the graph's per-idea cache, which drops that idea's bundle.
  4. After each rebuild the graph also writes nodes.jsonl and edges.jsonl as a snapshot for other tools to read. The app itself never reads that snapshot back.

What changes when it scales

Scaling the storage is a store adapter behind those four writers. A Postgres adapter replaces each read-and-rewrite with a table; Snowflake fits the same seam for the read-mostly analytics copy. The JSON-LD export, cafe export from the command line, already gives the graph with every link's provenance in a form a graph database or a warehouse can load today, without the adapter, with its schema beside it: an RDFS vocabulary and SHACL shapes the data validates against (pyshacl and rdf-validate-shacl find no violation), at a base IRI the workspace sets (an honest https://example.invalid/creators-cafe/ by default). A plain triple is a confirmed fact (a link waiting for the operator's Do it is only a reified cafe:Link with cafe:confirmed false), and a per-idea fact is a plain triple only where it holds for every idea; its consequence for each idea, idea DEPENDS_ON system, is a plain triple, so a plain SPARQL query gives the app's answer. SIMILAR_TO is owl:SymmetricProperty and written both ways, other names are skos:altLabel, and an AI link carries the passage it was read in (cafe:quote, checked against the idea's text) and when (cafe:readAt). docs/sparql-examples.rq has the queries a newcomer writes first, each with the app's answer beside it. Section 9 gives the table shape and the decisions that come first.

5 · How the AI processes an idea

Three layers over one idea: the facts, the meaning, and the words

The property graph says what the form said, the knowledge graph says what follows from it and why, and Deep read says what people actually wrote.

How the engine builds the graph, one idea end to end

The engine rebuilds the whole graph from files on every read, in five steps, in a fixed order, in milliseconds. NetworkX takes no part in it.

Figure 4 follows one real idea, the Travel policy assistant, through the build. Every example in it is a link in the practice workspace today, with the source the graph records for it.

  1. Forms. Each idea's record becomes typed stars and links: the idea, its submitter, the team, the people and their roles, and the form's choices. These are the facts as people stated them, each naming the form column it came from.
  2. AI links. The AI reads the free text and the emails and proposes links. Each is checked before it gets in: its types must fit the ontology, its quoted passage must be in the field it names, and anything below the confidence threshold waits for the operator's Do it.
  3. The operator's edits. Links added or removed, renames, aliases and merges are replayed in the order they were made. An edit that would break the rules is refused and reported.
  4. One name per thing. Throughout the first three steps, every name passes through the registry before a star is created. That is why "T&E policy", "travel policy" and "Travel & Expense policy" are one star.
  5. Rules, last. The inference rules run over everything above and add the facts nobody wrote, each with the rule and the facts behind it. Then the ontology check lists anything wrong.

Two choices make it trustworthy. Derived facts are never stored, only recomputed, so fixing one wrong fact fixes every conclusion drawn from it. And each source keeps its own file, so it is always clear who said what, and any layer can be rebuilt on its own. The detail of each layer follows.

Layer 1 The property graph: facts as stated

Every idea folder contributes a bundle of stars and links that is a pure function of its record: the idea star with its stage, function and region; a star for the submitter with a SUBMITTED link; one link per role for each team member (LEADS, SPONSORS, BUILDS, or plain RELATED); the team and division; the support asked for; and the form's choice columns, so two ideas that picked the same desired outcome share one star. There are thirteen kinds of star and twenty-one kinds of link in the built-in ontology (KIND_OF among them: a mailbox is a kind of email system), of which four are derived; a workspace may declare more. Each form link has confidence 1, is confirmed, and names the form column it came from. This layer is cheap and certain, and it is already enough for counts, lists, "who leads this" and "which stage is it at".

Layer 2 The knowledge graph: meaning, kept as data

Three small files turn those facts into something the app can reason over, and one AI call per idea feeds them.

  1. Extraction. When the operator asks to grow the universe for an idea, the AI reads the record, with names coded, and returns pain points, capabilities and systems named at a reusable level, each linked to the idea with a confidence and a description. The app keeps them in ai-links.jsonl with the provider and the form field it was read in as source (ai:claude:challenge) and the idea's id. A link whose confidence is at least 0.7 (graph: confirmAt in rules/settings.yaml) and that brings no new star is confirmed; one below it, or one that proposes a new star, waits for the operator's Do it. The same threshold holds for every path that writes AI links (a read, an Import, an answer, the inbox), and the build itself counts a link below it as confirmed only when the operator's Do it confirmed it, which only the Do it records (graph/confirmations.jsonl): a confirmedBy written into the file by hand counts as waiting and is named; a pending link never counts as confirmed. A link whose source does not name the AI and where it read, whose confidence is not a number from 0 to 1, or that picks a tool is dropped. Each link keeps the passage the AI quoted for it and when it was read; the app checks the quote against the idea's text and, when it is in another field than the one the AI named, records the field it is in. Before anything is saved, Deep read's label vectors are used, when they exist, to reuse a star that only differs in wording and to hold a near one for the operator.
  2. The registry. rules/entities.yaml gives the stars that keep coming back under other words a stable id, a label, its aliases, and sometimes a reference such as a catalogue id. When a star is born from a label, the registry resolves it first, by the label or any alias in one normal form that is also the star's id, so one name can never give two stars: "T&E policy", "T/E policy", "Travel and Expenses policy", "Travel & Expense policy" and "Travel policies" (with "travel policy" its alias) are one system, while C++, C# and C stay three. People are matched by their exact name, accents kept. A merge the operator does records the merged label as an alias, so the twin cannot come back at the next import.
  3. The inference rules. rules/inference.yaml holds four rules by default. Three are chains: an idea NEEDS a capability and that capability USES_DATA from a system, so the idea DEPENDS_ON the system; NEEDS plus BUILT_WITH gives USES; HAS_MEMBER plus SUBMITTED gives OWNS. The fourth links two ideas SIMILAR_TO each other when they share at least two capabilities, pain points or categories, naming the shared stars. Every stored link carries the ideas it is stated for, and the chains are scoped by them: same-idea for the data and the tool (a tool picked in one idea's design is that idea's, not every idea that shares the feature), same-idea-first for ownership (the team the idea's record names; the submitter's other teams only when it names none). A capability-level link stated for no idea applies only to the ideas whose own facts confirm it, never a workspace-wide spread. Chains may be any length that lines up. A derived link takes the lowest confidence of its inputs, is confirmed only when every input is, and carries source: rule:<name>, the ids of its inputs and every other way it is derived. It can never be stored by hand: the build refuses it. Each rule can be switched off in the file (false, no, off); a file that cannot be read is an error, not a silent fall-back.
  4. The ontology. rules/ontology.yaml says what each kind of star means, what colour it has in the universe, and which pair of types each link may join. It is applied over the built-in ontology, so the operator can rename "Division" without touching code, and the schema is open: a new kind (say Vendor) or relation (from, to, meaning, derived or not) is declared in the file, and the rules may chain it, with no code. Each build compiles the file into one frozen value passed to everything that reads that graph, never a table the app shares, so builds running at once keep their own. The build refuses what the ontology does not allow by any route, a hand-edited file included, drops it and names it in the check and the banner: an operator's idea, round, person or tool, the removal of an idea, team or person, the renaming of an idea or person, a role or tool link stored by hand, a system made a kind of itself or a loop of kinds, a merge of two kinds, an entities.yaml id whose prefix lies about its section, and an alias that makes a not-approved tool a name of an approved one. Confirmation is kept per idea: a fact confirmed for one idea is not confirmed for another that merely repeats it, and each link records who confirmed it (the form, the threshold, the operator's Do it, or an edit). Each Do it record is signed with a key kept outside the workspace (~/.cafe-ai/keys/), so editing the files by hand cannot forge one; what it cannot stop is code running as the operator's own account, which can read that key. cafe ontology check reads the three files and the graph, reports a duplicate alias, a rule it cannot take, a link whose ends are of the wrong type, a derived relation stored by hand, a link to a star that is not there or an id whose prefix is not its type's, and lists any operator edit whose stars are gone, any unscoped fact (with the command that settles it) and any AI link confirmed below the threshold, but never fixes anything. cafe ontology fix does, as a dry run first and with --apply, and never guesses an idea it cannot tell: a stale edit is listed with the stars it could point to, and only --repoint or --retire changes it.

buildGraph in src/graph/build.ts puts the layers in order on every read: the form bundles, then the AI links that pass the ontology, then the operator's edits in the order they were made, with a merge followed by any later edit at the merged star's id, then the rules last. Nothing derived is ever read from disk. A per-idea cache keyed on the record's hash and the registry's version means a rebuild recomputes only the ideas that changed.

Layer 3 Deep read: what people wrote

Neither graph can read prose. Deep read takes everything long in an idea folder that never becomes a star, the challenge, the current process, the email answers, the design, cuts it into passages of at most 1,200 characters with a 150-character overlap so a sentence on a seam is in both halves, and embeds each one on the CPU with a small sentence model, all-MiniLM-L6-v2 through the ONNX runtime. The model ships in the repo: cafe-app/models holds the four files the quantised load reads, config.json, tokenizer.json, tokenizer_config.json and onnx/model_quantized.onnx, with their SHA-256 in MANIFEST.json, so a fresh clone reads with no download and the app never downloads anything on its own.

The app looks for the model in CAFE_MODEL_DIR, then ~/.cafe-ai/models, then the bundled folder, and only ever reads the bundled one. The Hugging Face hub is contacted only if someone deletes that folder or sets a custom folder without the model: then the first Run downloads the same four files once into ~/.cafe-ai/models. When the firm blocks the hub, three things replace it, all in src/memory/model.ts: a firm mirror (CAFE_MODEL_MIRROR, an internal store that serves the same four paths under one base URL, with an optional bearer token), a manual import (cafe model import, a folder or a zip copied into the model folder and checked), and an export zip (cafe model export, so one person with access hands the model to the others). CAFE_MODEL_OFFLINE=1 forbids any host; a Run without the model then fails at once with one message naming those three ways in, in the pop-out and on the command line, never a stack trace.

The index keeps itself current. Each passage has a hash of its section and text. Every write into an idea folder names the idea on a touch bus; upkeep waits for five seconds of quiet, or thirty at most, then compares the touched ideas' passages on disk with the ones in the index and embeds only the fresh ones. A rename or merge refreshes the star labels and nothing else. The rule list is one pure function, decide in src/memory/upkeep.ts, and its reason is shown in the pop-out: never while the model is not on the machine, never when the switch is off, never over an index built with another model, never the whole workspace.

How the assistant uses all three

A question in the command bar is not answered by the AI. The AI writes a plan: a list of at most eight steps over the graph, from a fixed set, stars, follow, filter, role, intersect, path, rank, count_by, search and similar. The app runs the steps, so every count, name and lit star comes from the graph itself, and the trace shows each step with what it left. The guide the AI reads tells it to walk the graph first and to search the text afterwards, kept apart as "a reading", so an answer is built from facts and decorated with quotes. When a step uses a derived link, the reply says the rule: "derived by needs+uses_data", not "it seems".

What changes when it scales

The three rule files and the build are pure functions of their inputs, so they do not care whether the inputs came from files or from tables. The one open question is where the embeddings run: on each operator's CPU, as now, or once in the firm. Section 9 lists it as a decision.

6 · The three stages

Decision, design, roadshow: the same pattern three times

At every stage the AI reads the whole record and suggests, the people decide, the record grows, and the graph and Deep read see the growth before the next question is asked.

What it is

An idea moves through Review and Select, the Design series, and Launch and Learn. Each stage is a module under src/ with its own AI tasks, its own files in the idea folder, and the same shape: gather everything the idea holds, code the names, ask one question, check the reply in code, show it, and save on a click. Three stages means the pattern was written once and reused, not three different integrations.

Decision

"Suggest a decision" reads more than the form. The input in src/review/suggestInput.ts holds the form's answers, every email answer so far, whether a builder is named and whether attendance is confirmed, the flags, and what the knowledge graph holds for the idea: its pain points, its capabilities, the systems those capabilities use, and for each one how many other ideas need it. That last number is what lets the AI suggest Reuse when another idea already needs the same capability, and CSIC when the idea depends on a live system no approved tool may touch. The reply is a decision, a reason, the five criteria as true or false with the instruction to tick each only if the data supports it, at most five open questions, and any updates the answers justify. The operator sees the criteria as boxes they can change, the decision as one card, and a basis line that says "Based on the form, 3 answers and 4 graph links", so a new email visibly changes it. Saving writes review.md and never moves the idea by itself; it suggests the move. A CSIC route also writes csic-handoff.md with a source line under every field, and csic-handoff.jsonld, the idea's subgraph with its derived links, so the next level starts from the graph and not from a retelling.

Design

The design series is where the knowledge graph gains facts rather than only serving them. The data step profiles the team's files in code before the AI sees anything, and a column the check marks as masked stays masked in everything the AI is shown and on the page. The tool picker asks the AI to evaluate the approved tools, Microsoft Copilot, Copilot Studio, Power Apps, Dataiku, or a custom app that routes to CSIC, against the features; when the team picks one, the pick is saved on the idea and the next build writes a BUILT_WITH link from each covered capability to the tool, from which the rule derives USES for that idea (the pick is stated for the idea whose design made it; another idea that only shares the feature does not inherit it). That is what later answers "what breaks if a tool leaves the approved list". The brainstorm asks the team one question at a time and saves each answer on the idea at once; the diagram is drawn by the app from a checked specification, never by the AI. plan.md lists three to twelve tasks under the picked tool, and the starter kits hold a synthetic sample, the tool's own files and a test checklist. The app never writes application code.

Roadshow

The roadshow reads the record alone: the form, the decision, every answer, the features, the tool, the design, the plan and the dates. It does not query the graph. "Suggest" lists only what the deck still needs from the team; each answer the operator pastes is saved on the idea with the source "roadshow" and rewrites the "learned since the form" brief, and that write is what Deep read picks up. "Build the deck" asks the AI for a structure, not slides: a title, six to sixteen slides each with a kind from a fixed list, points, a visual from a fixed list, speaker notes and minutes. The code then checks it. A point that contains a value word, ROI, savings, KPI, payback, business case, a currency amount, is removed, because the Café has no value story, CSIC does. A figure the record does not hold is removed. A missing title or team slide is added, and timings are scaled to about ten minutes. Only then does the app draw deck.html, deck.pptx, script.md and run-of-show.md. Photos are checked by their bytes, copied into the folder, and never sent to the AI.

What the graph and Deep read add at each stage

Decision: shared capabilities and systems, with how many other ideas need them, which the form alone cannot show. Design: the tool pick becomes a fact every other idea inherits by rule. Roadshow: the team's answers become passages Deep read can quote, so the next operator question, "what did the team say was hard", finds them. Each stage adds to the record, upkeep re-reads only that idea, and the next graph read includes the growth.

What changes when it scales

Nothing in the stages. They call the connector and the stores and never a provider or a file path directly, which is the whole reason the two seams in section 9 are enough.

7 · Why three layers

What plain RAG cannot give, and which layer answers which part

A passage is not a fact: retrieval can quote what someone wrote, but it cannot count, cannot follow a dependency, and cannot say why it believes something.

Plain RAG is retrieval: cut the documents into passages, embed them, fetch the nearest few, and let the model write an answer from them. It is Deep read alone. It is good at "what did the travel desk say about emails" and poor at everything below, because a passage is not a fact. The table lists questions operators actually ask in the command bar. Read each row left to right: what retrieval alone would do, what the app does, and which layer did the work. Three questions, end to end

"Which ideas would need rework if the expense system changes, and what did their teams say about data access?"
  1. KG The registry resolves "the expense system" to one star, whatever the form called it.
  2. KG The plan follows DEPENDS_ON inwards to the ideas. Each hit is a derived link, so the reply says "derived by needs+uses_data via Expense extraction" and names the capability in between.
  3. PG A role step lists the lead and builder of each idea from the records.
  4. DR A second query searches "data access" with last: true, so only those ideas' passages are read; the quotes come back per idea, kept apart as a reading with a score.
"Which capabilities do GSS and BSI both need, and which ideas need each?"
  1. PG Start from the ideas whose function is GSS, follow NEEDS to their capabilities.
  2. PG Intersect with the same two steps for BSI.
  3. KG The capabilities are shared only because the registry and the AI's "reusable level" instruction made "parse a PDF" one star across both teams' ideas.
  4. PG Follow NEEDS back to ideas with group: true, so the answer reads "Document parsing: I1, I3; Workflow routing: I2, I4". Retrieval has no step that can do this.
"Is the travel bot the same thing as the expense assistant?"
  1. KG Follow SIMILAR_TO from the first idea. A hit names the shared stars: "by shared stars: Document parsing, Policy lookup".
  2. DR If Deep read has run, a similar step adds ideas whose prose reads alike, with a score, listed after the fact-based hits as "by reading, also".
  3. PG The decision stage uses the same shared stars: "also needed by 2 ideas" is what makes it suggest Reuse.

Why not one bigger layer

Each layer is small, separately testable, and deletable. The AI links can be re-read. The index can be rebuilt. The rules can be edited by hand and switched off one at a time. None of them blocks the others: with no index, every search step is simply absent from the plan and the graph answers as before. A single store that did all three would be harder to trust and impossible to explain line by line, and "explain line by line" is the Café's whole promise to the people whose ideas it holds.

8 · NetworkX for analysis

NetworkX for analysis, our own engine for building and reasoning

The app builds the graph; NetworkX analyses it. Each does what it is best at, and the operator keeps the last word.

Colleagues asked "why not NetworkX". The honest answer is that the question was never either-or. Building this graph is domain work: every link carries who said it, with what confidence and for which idea, the registry keeps one identity per thing, and the rules derive new links in a fixed order with their inputs named. That stays in our TypeScript engine, where the operator can read it line by line. Analysing the finished graph as a whole is algorithm work, and there NetworkX is the standard: centrality, communities, paths, components and link prediction, well tested and well known. So the app now hands its graph to NetworkX for exactly that.

How NetworkX works inside the app, in four steps

NetworkX is a Python library that holds a graph in memory and runs well-known algorithms over it. It knows nothing about ideas, capabilities or the Café. The app does the knowing: it builds the graph, decides which links are trustworthy enough to analyse, and turns NetworkX's numbers back into sentences the operator can act on. Figure 6 shows the round trip. It takes well under a second on the practice workspace, and the result is cached until the graph changes.

What NetworkX sees in the practice workspace

Figure 7 is a simplified slice of the real graph: the seven ideas and the two capabilities NetworkX ranks highest. Four ideas need Request handling. Five need Document text extraction, and two of those five also sit on the left. Those two capabilities are the bridges: most shortest paths between ideas pass through one of them. That is exactly what betweenness centrality measures, and it is why they top the ranking.

Eight examples, with the real answers

Each example below was run on the practice workspace on 1 November, over confirmed stored facts. It shows the question as the operator would ask it, what NetworkX computed, the answer, and what the app does with it.

1. "Which capability holds the most ideas together?"
  1. NetworkX runs betweenness centrality: for every pair of stars, how often a star lies on the shortest path between them.
  2. Answer: Request handling 0.31, needed by 4 ideas. Document text extraction 0.27, needed by 5. Then Record update, Policy question answering and Summary report generation.
  3. Why it helps: these are the shared building blocks. Build one well and several ideas benefit, so they are the strongest reuse case to put to CSIC. They are also the biggest single point of failure if a tool behind them is withdrawn.
2. "How is the GSS team connected to the Expense system?"
  1. NetworkX runs shortest paths, avoiding form-choice hubs, and the app names the link on every hop.
  2. Answer: 4 hops, 2 paths. GSS has member Ingrid Solberg. She leads and submitted Expense anomaly finder. It needs Anomaly detection in claims, or Policy compliance checking. Both use data from the Expense system.
  3. Why it helps: it shows who to talk to before the Expense system changes, and through which capability the change would reach the team.
3. "What do the Travel policy assistant and Meeting notes to actions have in common?"
  1. NetworkX runs a shortest path between two ideas.
  2. Answer: 2 hops. Both need Document text extraction.
  3. Why it helps: two ideas from different teams, with nothing in common in their wording, turn out to need the same component. That is a conversation the Café can start.
4. "Do the ideas fall into natural groups?"
  1. NetworkX runs Louvain community detection over the capabilities and pain points the ideas share, with a fixed seed, and reports the modularity score.
  2. Answer: three tentative groups: the two policy bots, the desk booking and expense ideas, and the three document-and-deadline ideas. Modularity is 0.19, below the 0.3 the app requires, so it says "no clear groups".
  3. Why it helps: honesty. With seven ideas, any split is weak, and the app refuses to present one as real. At firm scale, a score above 0.3 would point to a genuine programme of related ideas.
5. "Is anything cut off from the rest?"
  1. NetworkX runs connected components.
  2. Answer: one component, all 107 analysed stars connected. Nothing is isolated.
  3. Why it helps: an idea imported with no capabilities, or a system nobody links to, would show up here at once. It is a quality check on the graph itself.
6. "What links are probably missing?"
  1. NetworkX runs link prediction (Adamic-Adar and Jaccard): for each idea, its three closest peers, and the links most of them have that it lacks. A suggestion needs two shared stars per peer and two peers agreeing, on confirmed links only.
  2. Answer today: none. NetworkX considered 15 candidates, and none passed on confirmed evidence. In an earlier build that still counted unconfirmed links, it suggested that Onboarding checklist helper needs Key term extraction. The app now withholds suggestions like that until the links behind them are confirmed.
  3. Why it helps: when it does fire, the suggestion arrives as a proposal card with its evidence. Nothing enters the graph until the operator presses Do it.
7. Design: "Record updating process" is typed as a new feature
  1. NetworkX runs link prediction across all ideas, not just the one being designed.
  2. Answer: the design stage flags it as looking like the existing Record update capability, which three other ideas already need: Vendor contract summariser, Desk booking assistant and Procurement FAQ bot. Wording alone would not have caught it.
  3. Why it helps: it stops the same capability from being built twice under two names.
8. Decision: the AI suggests what to do with an idea
  1. NetworkX supplies the centrality rank of the idea's capabilities and systems, the grouping verdict, and any likely missing link, all marked as analysis.
  2. Answer: the suggestion's "based on" line names the network analysis. In testing, the AI's reason for "reuse" cited the Procurement FAQ bot sharing the same central capabilities.
  3. Why it helps: the decision weighs the whole portfolio, not just the one form in front of the operator.

The honest scale note. With seven ideas, an experienced reader can see most of this by eye, and NetworkX adds little that the assistant's own steps could not count. Its value grows with the portfolio. With hundreds of ideas across divisions, nobody can see the bridges, the groups or the missing links by eye, and these same eight questions run unchanged.

How it is wired

  1. The app builds the graph as always, then writes it as node-link JSON to the standard input of python -I -S py/network.py.
  2. The script imports NetworkX straight from the official wheels shipped in cafe-app/vendor/networkx: 3.7 for Python 3.12 and later, 3.2.1 for 3.9 to 3.11 (macOS's own python3). MANIFEST.json holds their SHA-256; the licence is BSD-3. -I -S keeps out anything installed on the machine, and only pure-Python algorithms are used, so there is no download, no numpy and no scipy, which matters on a locked-down PC.
  3. The answer comes back as JSON, deterministic (fixed seeds, sorted lists), validated, and cached per graph version.

Two rules it keeps

  • Confirmed stored facts by default. The analysis reads the form, the AI's links and the operator's edits, and leaves out every link still waiting for Do it, for every analysis, not only suggestions (the pop-out's Waiting links switch, or --with-unconfirmed, adds them, and every output says which it read). Derived links are added only when asked (--with-derived, or the pop-out's switch), and every output says which. Derived links are conclusions, not observations; an analysis should not count them twice.
  • Human last control. NetworkX never writes the graph. A link it predicts is a proposal the operator accepts, or not, with the assistant's Do it, and it is labelled "suggested by NetworkX" only when it is among NetworkX's suggestions on the graph as it is now.
  • Rankings and suggestions that mean something. Centrality and link prediction leave the form choices (outcomes, support, categories, beneficiaries) out by default, so the rankings are capabilities, systems, people and teams. Link prediction compares ideas by the capabilities and pain points they share and capabilities by the systems they use, with two shared stars per peer and two peers per suggestion, on confirmed links only. A system's "ideas" are the ideas that depend on it.
  • Saying what it found, and what it could not. Clusters are read from the capabilities and pain points ideas share (form choices, people and teams left out) and come with NetworkX's modularity and a plain verdict: below 0.3 "no clear groups", and then the pop-out shows the groups as tentative, the assistant says there are no clear groups and the stages pass no cluster on. The practice workspace scores 0.19. Cycles are looked for only along relations the ontology lets loop; with the built-in one none can (Idea → Capability → System cannot close and the build refuses a loop of KIND_OF), so the analysis says it has nothing to look for. Paths keep off the form-choice hubs.

Where it shows up, end to end

  • CLI and API: cafe network check | stats | central | clusters | path A B | isolated | suggest | cycles and GET /api/network, both read-only (cycles says when the ontology lets nothing loop).
  • The assistant: a network step for "which capability holds the most ideas together", "which ideas naturally group together", "how is this team connected to that system", "is anything isolated", "what links are probably missing". The trace says "NetworkX betweenness centrality over confirmed stored facts"; suggested links come back as Do it cards. Outside NetworkX, the assistant's own steps say "not confirmed" for every stored link they cross that waits for Do it, and its links step says where any link came from (the operator's edit and date, the AI's field, quoted passage and time, the form's column).
  • The Network pop-out: the size line, the central stars, the clusters (one click lights a cluster in the universe), anything cut off, and the likely missing links with a Propose button.
  • Decision: the suggestion reads the grouping verdict, the idea's cluster when the groups are real, the centrality rank of its capabilities and systems, and its likely missing links, and its basis says so; each graph fact that rests only on an unconfirmed link is sent marked confirmed: false.
  • Design: the duplicate check also flags a feature that matches a capability other ideas already need, naming them; NetworkX's prediction lowers the wording bar.
  • CSIC hand-off: the JSON-LD carries one Analysis node whose content is a JSON literal, labelled as analysis and never links between the stars. A suggested capability → system link is stamped with the idea it was suggested for when accepted.
  • Analysts: cafe export --format networkx writes node-link JSON that networkx.node_link_graph loads; docs/networkx-example.py is a 15-line start.

Without Python 3.9 or later, every NetworkX feature says so in one line and the rest of the app works exactly as before.

9 · Where it goes next

The Firm AI Gateway and Postgres or Snowflake

Two arrows change and nothing in between: the AI connector points at the firm's gateway, the file writers point at the firm's warehouse, and the names, the checks, the rules and the universe stay as they are.

Path one: the Firm AI Gateway

What exists today. The connector in src/ai/connector.ts holds an ordered list of providers and asks each whether it is available. A provider is one file under src/ai/providers/: claude.ts, copilot.ts, vscode.ts, fake.ts. The interface is small: an id and a label, available(), complete(prompt, { timeoutMs }) returning text, and an optional look(file, prompt) for a picture. Everything the app cares about, coding the names, the schema check, the one retry, the timeout ceiling, the card, happens around the provider, never inside it. The VS Code helper is already an HTTP provider: it reads a port and a token from a file in the operator's home folder, posts the prompt, and caps the reply.

What the change is. One new file, gateway.ts, implementing the same interface: available() checks the firm token and the gateway's health, complete() posts the coded prompt over HTTPS with that token and returns the text. Add it to the provider list, add gateway to the choices the settings accept, and the rest of the app does not know it happened. What the firm gains is what a gateway is for: authentication with the firm's identity rather than a personal CLI login, an audit record of every call, a choice of models made centrally, and rate limits the firm sets.

What stays the same. The name coding, because it runs before the prompt exists. The schema check and the retry, because they run on the text that comes back. Do it, because a reply is still a card until the operator clicks. The inference rules, the ontology check and the universe, because they never see a prompt.

Path two: Postgres or Snowflake

What exists today. Four files write the Café's state: src/ideas/store.ts (one idea.yaml per folder), src/graph/store.ts (ai-links.jsonl), src/graph/operator.ts (operator.jsonl) and src/memory/index.ts (index.jsonl, state.json, labels.jsonl). Each reads a whole file and writes it back atomically. The graph is never stored as such; it is rebuilt from those inputs on every read. And cafe export already writes the whole graph as JSON-LD, with every link's source, confidence, status and derivation, which a warehouse can load today with no adapter at all.

What the change is. A store adapter: the same four read-and-write functions, backed by tables instead of files, chosen by a setting. The table shape falls out of the files, and the provenance columns are not optional, because they are what the trace and the ontology check read:

  • ideas: id, title, stage, function, region, round, the record as a document column, updated at.
  • people: name and the role per idea, from the record's team list.
  • stars: id, type, label, aliases, reference; the registry's rows plus the stars born from forms and extraction.
  • links: from, relation, to, description, source, confidence, confirmed, idea, status, and for a derived link its rule and the two input link ids.
  • operator_edits: id, at, status, kind, and the edit's fields; never deleted, undone by status, applied in order.
  • passages: id, idea, file, section, kind, text, hash, embedded at, and an embedding column of the model's dimension.

Postgres fits the writing side: many operators, one graph, row-level writes, and an embedding column through its vector extension. Snowflake fits the reading side: firm reporting over every round, joins to other firm data such as the system catalogue or the team directory, and a place the JSON-LD export can land unchanged. The two are not exclusive; the usual shape is Postgres behind the app and Snowflake as the analytics copy.

What stays the same. The build: buildGraph takes ideas, AI links, rounds, operator edits, a registry and rules as plain values, and does not know where they were read from. The inference rules and the ontology check, for the same reason. Deep read's chunking and upkeep logic, which compare hashes, not files. The universe, which reads the graph over the same JSON routes.

The model behind the firm proxy

Deep read's model ships in the repo (cafe-app/models, about 23 MB, checksummed in MANIFEST.json), so the laptop version fetches nothing from outside the firm: a clone from the firm's GitHub has the model, and no host is ever contacted for it. The Hugging Face hub is used only if someone deletes that folder or points CAFE_MODEL_DIR at a folder without the model; then the first Run downloads it once into ~/.cafe-ai/models, and behind a proxy that blocks the hub this is already solved without either path above: a firm mirror in Artifactory or Nexus serves the four files under one base URL and CAFE_MODEL_MIRROR points the download there; or one person with access runs cafe model export and the others run cafe model import; and CAFE_MODEL_OFFLINE=1 makes sure nothing ever tries the hub. The gateway path does not change this: embeddings stay on the operator's CPU unless decision 3 below moves them into the firm.

What would need deciding before doing either

  1. Who owns the graph when there are many operators. Today one operator's edits are the last word. With several, a star merged by one and renamed by another needs a rule: last write wins, a review queue, or edits scoped to the round.
  2. How operator edits merge. The log is applied in order, and a merge re-points later edits. With two logs the order has to be defined, or the log has to become one shared, ordered table from the start.
  3. Where Deep read's embeddings run. On each operator's CPU, as now, with the index per operator; or once in the firm, with one index, which puts the passages, the words people wrote, into the warehouse. The gateway path does not decide this; it is a separate choice.
  4. Which warehouse, and for what. Postgres for the app's writes, Snowflake for the firm's reads, or one of them for both. The Neo4j and Snowflake comparison exists as a separate reference page and is the next read for that choice.
  5. When a graph database enters. NetworkX already does the analysis (section 8); Neo4j comes in only if a graph outgrows an in-process rebuild. The adapter seam is where Neo4j would sit if it ever does.

The honest summary. Both paths are real because the seams are already in the code: one interface for providers, four named writers for state, and an export that carries provenance. Neither path is built, and neither should be until the Café has more than one operator or more than one laptop's worth of ideas. The decisions above come before the code.

What to remember

Five points

The shape
  1. One process, one folder, one laptop. Nothing installed on a server, nothing sent anywhere, and the whole state can be zipped or deleted.
  2. The AI answers; the operator decides. Names are coded before the prompt, the reply is checked against a schema, and nothing changes until Do it.
The understanding
  1. Three layers, each for a kind of question. Facts as stated, meaning derived by rules with provenance, and the words people wrote.
  2. Every answer shows its working. A derived link names its rule and its inputs; a stated link names the form column, the AI read, or the operator's edit.
The future
  1. Two seams, already there. A gateway is one more provider file; a warehouse is a store adapter behind four writers. Everything between them stays.
